# Архитектура Контентфабрики

Документ описывает текущую реализацию приложения. Порядок подключения сервера и CI/CD находится в [инструкции развёртывания](../deploy/SETUP.txt).

## Сервисы

| Сервис | Назначение | Технологии |
|---|---|---|
| **Frontend** | Рабочий кабинет, редактор раскадровки, просмотр и управление материалами. В production Nginx раздаёт собранный интерфейс и проксирует запросы к сервисам. | React, Vite, Tailwind CSS, Nginx |
| **Backend** | API, аккаунты и ключи, проекты и контент-планы, управление генерациями, локальная сборка видео, работа с галереей и публикациями. | Python 3.11, FastAPI, SQLite, FFmpeg |
| **Renderer** | Серверный рендер композиций Remotion. Использует тот же том готовых файлов, что и backend. | Node.js, Remotion, Chromium, FFmpeg |

В production-конфигурации кабинет доступен на порту **5175**, backend — **8000**. Renderer работает внутри сети Compose на порту **3100**. Отдельный сервис `volume-init` подготавливает права на постоянные каталоги до запуска backend.

Nginx направляет `/api`, `/videos`, `/thumbnails`, `/gallery` и `/video` в backend, а `/render` — в renderer. Для остальных маршрутов работает SPA fallback. При открытии кабинета через localhost существующая клиентская конфигурация также обращается напрямую к `127.0.0.1:8000`.

## Обработка видео

### AI Shorts

1. Backend получает бизнес-бриф, URL или готовый текст. Gemini формирует анализ, сценарий и постановку сцен.
2. Пользователь редактирует материал в кабинете. Контент-план и рабочие состояния сохраняются отдельно для каждого проекта и пункта плана.
3. Озвучка создаётся через ElevenLabs либо MiniMax через fal.ai. Её можно прослушать отдельным этапом; готовые записи используются при сборке видео.
4. Изображения и клипы создаются через fal.ai. Режим определяет, будет ли это говорящий аватар, отдельные сцены или несколько сцен одной генерацией. Ранее полученные подходящие материалы могут использоваться повторно.
5. Локальный FFmpeg собирает клипы, речь, субтитры и музыку. Хронометраж согласуется с озвучкой.
6. Готовый файл и метаданные попадают в галерею. Следующие изменения могут создавать новые версии; публикация выполняется отдельным запросом к Upload-Post.

Основной монтаж AI Shorts выполняется в Python/FFmpeg. Renderer обслуживает композиции Remotion; часть операций с такими композициями также доступна в браузере через WebCodecs.

### Нарезка длинного видео

Загрузка файла или получение исходника через yt-dlp → транскрипция faster-whisper → анализ Gemini → извлечение фрагментов → вертикальное кадрирование → субтитры и эффекты. Для определения сцен и сопровождения человека используются PySceneDetect, OpenCV, MediaPipe и YOLO.

Генеративные модели работают у внешних провайдеров. Локальная транскрипция настроена на Whisper `base`, CPU и INT8; production backend устанавливает CPU-сборки PyTorch. GPU для этой конфигурации не требуется.

## Данные и состояние

| Где | Что хранится |
|---|---|
| **SQLite в `output/openshorts.db`** | Пользователи, сессии, зашифрованные ключи провайдеров, бизнес-профили, контент-планы и сохранённые рабочие состояния. |
| **`output/`** | Видео, версии, изображения актёров, кадры, озвучка, субтитры и метаданные. Backend и renderer используют общий том. |
| **`uploads/`** | Загруженные исходные материалы. |
| **`.env` на сервере** | Настройки экземпляра и секрет хранения ключей; при необходимости — серверные ключи провайдеров. |
| **Память процессов** | Очереди, текущие статусы генераций, публикаций и серверных рендеров. |
| **Хранилище браузера** | Локальные настройки и копии рабочего состояния, которые интерфейс сопоставляет с сохранёнными данными аккаунта. |

Production Compose использует фиксированные Docker-тома `content-fabric-output` и `content-fabric-uploads`. Папка развёртывания содержит `.env`, `compose.yml` и `images.env`; она отделена от checkout GitHub runner.

При обновлении образы и контейнеры заменяются, а тома и существующий `.env` сохраняются. Резервная копия должна включать данные и секрет хранения ключей: без прежнего секрета сохранённые API-ключи не расшифровать. В кабинете доступны экспорт и импорт backup; такой архив содержит чувствительные данные.

Промежуточные файлы и старые записи задач могут очищаться автоматически. Это не заменяет резервное копирование готовых материалов.

## Задачи и ограничения

- `MAX_CONCURRENT_JOBS` ограничивает число одновременно обрабатываемых задач backend. В конфигурации развёртывания для N100 устанавливается **1**; значение по умолчанию в самом приложении — **5**.
- Одна задача может параллельно отправлять несколько запросов провайдеру. Ограничение задач не равно ограничению всех внешних запросов или счетов за генерацию.
- Очереди и активные статусы не являются постоянными. Обновлять backend и renderer следует после завершения работ: перезапуск не гарантирует продолжение активной генерации.
- API renderer запускает рендеры отдельно и не использует семафор backend. Для высокой параллельной нагрузки ему потребуется собственная очередь.
- Текущая схема рассчитана на один экземпляр backend. Несколько процессов или реплик потребуют общего постоянного хранилища задач и согласованной работы с файлами.
- Расчёт стоимости может содержать оценки и неизвестную часть. Интерфейс сохраняет это различие; оценка не подтверждает списание у провайдера.

## Поставка и проверка доступности

[Workflow](../.github/workflows/ci-cd.yml) проверяет backend, frontend и скрипт развёртывания, затем публикует три Linux/amd64-образа в GHCR. Обновление домашнего сервера выполняет отдельный self-hosted runner после включения соответствующей настройки репозитория.

[Скрипт развёртывания](../deploy/deploy.py) скачивает образы, применяет Compose и ожидает healthcheck. При неудаче он пытается вернуть предыдущую конфигурацию и версию образов. Этот возврат не откатывает содержимое базы данных.

Проверки доступности: backend — `/api/config`, renderer — `/health`, frontend — `/health`. Они проверяют сервисы приложения; доступность и баланс внешних провайдеров оцениваются при обращении к ним.
